# 02. 계층의 문제점

---

## 0. 개요

### 3계층 아키텍처

- 웹 -> 도메인 -> 영속성
- 웹 계층(web layer) : HTTP 요청을 받고 응답을 돌려주는 계층, 비즈니스 판단은 하지 않는다.
- 도메인 계층(domain layer) : 비즈니스 규칙을 처리하는 계층, HTTP나 SQL은 몰라야 한다(이상적).
- 영속성 계층(persistence layer) : DB에 저장하고 조회하는 계층, 레포지토리와 JPA 엔티티가 여기에 속한다.
- 웹 계층이 요청을 받아 도메인 계층의 서비스로 라우팅한다. 서비스에서는 비즈니스 로직을 수행하고
  영속성 계층의 컴포넌트를 호출해 데이터베이스에 들어있는 도메인 엔티티의 현재 상태를 조회하거나 수정한다.

### 계층 아키텍처 더 알아보기

#### 계층(layer)과 티어(tier)

- 계층(layer) : 코드를 역할별로 나눈 논리적인 구분이다. 패키지나 모듈로 나뉜다.
- 티어(tier) : 물리적인 배치 구분이다. 예를 들어 브라우저 / WAS 서버 / DB 서버로 나뉜다.
- Spring 애플리케이션 하나(티어 1개) 안에도 계층은 3개가 있을 수 있다.

#### 엄격한 계층과 느슨한 계층

- 엄격한 계층(strict) : 바로 아래 계층만 호출할 수 있다. 웹 -> 도메인 -> 영속성 순서로만 간다.
- 느슨한 계층(relaxed) : 아래 계층이면 건너뛰어도 된다. 컨트롤러가 레포지토리를 바로 호출할 수 있는 식이다.
- 느슨한 계층은 당장은 편하다. 하지만 "나쁜 의존성이 스며드는" 대표적인 통로가 된다.

#### 계층 사이의 데이터 전달(DTO)

- 계층 사이에 데이터를 넘길 때 선택지가 존재한다. JPA 엔티티를 그대로 넘기는 선택지와 계층마다 전용 객체(DTO)를 만드는 선택지가 있다.
- 엔티티를 그대로 쓰면 코드는 적다. 하지만 웹 응답 형식이 DB 구조에 묶이고, DB를 바꾸면 API까지 바뀐다는 치명적인 단점이 존재한다.

#### Spring에서의 계층

- 웹 계층 : `@Controller`, `@RestController`
- 도메인 계층 : `@Service`
- 영속성 계층 : `@Repository` + Spring Data JPA 인터페이스
- 위 어노테이션들은 모두 `@Component`의 확장이라서 빈 등록 방식은 동일하다. 이름으로 역할을 드러낸다는 의미가 크다.
- 다만 어노테이션들이 계층 사이의 의존 방향을 강제하지는 않는다. = 충분한 가드레일을 제공하지 않는다.

### 계층 아키텍처의 장점

- 관심사의 분리 : 계층마다 맡는 일이 하나라서 코드를 찾고 고칠 위치가 분명해진다. 기존 기능에 영향을 주지 않고 새로운 기능을 추가할 수도 있다.
- 단방향 의존 : 의존이 위에서 아래로만 흐르기 때문에 아래 계층은 위 계층을 모른다.
- 교체 가능성 : 계층을 적절히 구현하면 도메인 로직을 웹·영속성 계층과 독립적으로 둘 수 있고, 도메인 로직에 영향을 주지 않고 웹이나 영속성 기술을 교체할 수 있다.
- 계층 단위 테스트 : 아래 계층을 mock으로 바꿔서 한 계층만 테스트할 수 있다.
- 익숙함 : 대부분의 개발자가 이미 알고 있어서, 새 팀원이 들어와도 배우는 비용이 적다.

### 계층의 문제점

- 변화에 매우 취약해서 유지보수하기 어렵다.
- 나쁜 의존성이 스며들어 시간이 지날수록 소프트웨어를 변경하기 점점 더 어렵게 만든다.
- 계층은 아키텍처를 올바른 방향으로 유지하는 데 필요한 가드레일을 충분히 제공하지 않는다.
- 유지보수성을 유지하기 위해서는 인간의 규율과 성실함에 너무 많이 의존해야 한다.
