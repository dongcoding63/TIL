# 01. 유지보수성

---

## 0. 개요

### 아키텍처란?

- 정의 : 어떤 목적을 가지고 시스템의 구조를 설계하는 것

---

## 1. 유지보수성은 도대체 무엇을 의미하는가?

### 유지보수성이란?

- 품질 요구사항(비기능적 요구사항) 중 하나

### 유지보수가 가능하다는 것

- 소프트웨어가 유지보수가 가능 -> 변경하기 쉽다는 의미
- 변경하기 쉽다는 것 -> 유연하고 아마도 모듈화되어 있을 것, 비용 효율적

### 유지보수하기 쉬우면 얻는 것

- 따라서 유지보수하기 쉽다면 필요에 따라 확장 가능하고, 안전하고, 신뢰할 수 있고, 성능이 좋도록 진화시킬 수 있을 것
- 변경 또한 쉽기 때문에 소프트웨어를 다른 시스템과 상호운용하도록 변경할 수 있음
- 테스트 가능성도 높다는 것을 의미 -> 유지보수 가능한 소프트웨어는 테스트하기 쉬운, 더 작고 간단한 컴포넌트로 설계될 가능성이 높기 때문

> 즉 소프트웨어가 유지보수가 가능하다면 기능적으로나 비기능적으로 어떤 방향으로든 진화시키기가 더 쉽다

---

## 2. 유지보수성이 기능성을 가능하게 한다

> "유지보수성이 기능성보다 더 중요하다"

- 소프트웨어 -> 가치를 제공해야 한다. 하지만 유지보수성을 희생하면서까지 가치를 제공하는 일은 없어야 한다.
- 유지보수하기 쉬운 소프트웨어 시스템은 유지보수하기 어려운 소프트웨어 시스템에 비해 전체 수명 주기 동안 소모되는 비용이 적다
- 유지보수성은 평화를 촉진한다. 변경 비용에 반비례하고, 따라서 갈등이 생길 확률도 반비례한다
  - 여기서 갈등은 기능을 원하는 쪽(기획·비즈니스)과 개발자 사이의 갈등. 변경 비용이 크면 요청 하나하나가 부담이 되어 부딪히기 쉽다

### 사전 설계는 얼마나 해야 할까?

- 그러면 프로그래밍을 시작하기도 전에 유지보수 가능한 아키텍처를 계획하는 데 많은 시간을 보내야 할까(대규모 사전설계, BDUF)?
- 하지만 소프트웨어 유지보수성의 씨앗을 심기 위해서는 어느 정도의 사전 설계(SDUF)가 필요, 이를 통해 시간이 지남에 따라 아키텍처를 원하는 방향으로 진화시키는 것을 용이하게 할 수 있다
- BDUF : Big Design Up Front
- SDUF : Small Design Up Front

---

## 3. 유지보수성은 개발자 즐거움을 만들어낸다

- 변경 비용에 직접적인 영향을 주는 것 말고도 유지보수성은 또 다른 이점이 있다. 바로 개발자를 행복하게 만든다는 것이다
- 개발자가 자신의 업무를 잘 수행하는 데 필요한 맥락을 제공한다는 의미다
- 개발자 즐거움은 개발자 생산성과 직접적인 연관이 있다(양방향 상관관계)

### SPACE 프레임워크

- 만족도와 웰빙
- 성과
- 활동
- 의사소통과 협업
- 효율성과 흐름

> 유지보수성은 개발자 즐거움과 생산성에 직접적인 영향을 미치며, 개발자 즐거움은 재직률에도 영향을 미친다

---

## 4. 유지보수성은 의사결정을 지원한다

- 소프트웨어 시스템을 구축할 때 우리는 매일 문제를 해결한다. 우리가 직면하는 대부분의 문제에 대해 하나 이상의 해결책이 있다.
- 이러한 해결책 중 하나를 선택하기 위해 결정을 내려야 한다.
- 여러 선택지 중에서 결정해야 할 때마다 미래에 코드를 더 쉽게 변경하게 만드는 선택지를 선택하면 된다.
- 유지보수성을 가장 크게 개선하는 것을 선택하면 된다

ex)
- 코드 중복을 발견했을 때 반복하지 마라 (DRY 원칙, Don't Repeat Yourself)
- 코드의 테스트 가능성을 높이기 위해 의존성 주입을 사용한다 (Spring의 생성자 주입)
- 객체 생성을 더 간단하게 만들기 위해 빌더를 도입한다 (빌더 패턴, Lombok `@Builder`)

### 주의할 점

- 특정 맥락에서 올바른 의사결정이라도 유지보수성을 개선하지 않거나 심지어 유지보수성을 떨어뜨리는 방법일 수 있다
- 하지만 기본적으로 유지보수성을 택하는 것은 일상적으로 내리는 의사결정을 단순화하는 결과로 이어진다

---

## 5. 유지보수성 유지하기

### 질문

- 우리가 코드에 가하는 변경이 유지보수성을 높이는지(또는 적어도 떨어뜨리지는 않는지) 어떻게 알 수 있을까?
- 시간이 지남에 따라 유지보수성을 어떻게 관리해야 할까?

=> 유지보수 가능한 코드를 용이하게 하는 아키텍처를 만들고 유지하는 것

### 좋은 아키텍처

- 좋은 아키텍처는 코드를 탐색하기 쉽게 만든다.
- 코드를 쉽게 탐색할 수 있으면 기존 기능을 수정하거나 새로운 기능을 추가하기가 무척 쉽다
- 애플리케이션을 구성하는 컴포넌트들 사이의 의존성이 명확하고 서로 얽혀 있지 않다

=> 좋은 아키텍처는 유지보수성을 높인다

=> 더 나아가 좋은 아키텍처는 개발자 즐거움, 개발자 생산성, 개발자 재직률, 의사결정에 도움이 된다

### 이 책에서 학습할 것

- 코드를 어떻게 구조화할 것인가?
- 코드 파일들을 컴포넌트로 어떻게 그룹화할 것인가?
- 그러한 컴포넌트 간의 의존성을 어떻게 관리할 것인가?
- 어떤 의존성이 필요하고, 코드를 변경에 유연하게 만들려면 무엇을 하지 말아야 하는가?

=> 이 책의 목적이자 내가 학습해야 하는 것

> 책에서 배운 내용을 토대로 이 책의 아이디어들을 실험해보고, 나의 것으로 만들기 위해 수정하고, 특정 맥락에서 적절하다고 생각했을 때 이 책에서 배운 바를 적용할 수 있는 것
